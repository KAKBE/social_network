# 6. Архитектурные решения (ADR)

## Обоснование стиля через требования

| Требование | Как влияет на стиль |
|---|---|
| Команда из трёх человек (слайд 11), защита RAT-PoC через 2 дня | минимум развёртываемых единиц и движущихся частей |
| Масштаб MUP — 15 пользователей (слайд 10), ≈ 0,09 запр./с в пике (05) | распределённая архитектура не нужна для нагрузки |
| Данные сильно связаны: дружба определяет видимость рекомендаций и мест (US-06) | правило доступа должно жить в одном месте рядом с данными |
| Поставщик карт не выбран (R1, R2) | внешние сервисы — за адаптерами, заменяемы настройкой |

Отсюда: **модульный монолит** (один Backend API) + одностраничный Web Client + одна PostgreSQL — ровно контейнеры принятой C4 уровня 2.

---

## ADR-1. Один Backend API (модульный монолит) вместо набора служб

- **Статус:** принято (совпадает с C4, Diagrams.pdf, стр. 2).
- **Контекст:** три человека, срок 2 дня до RAT-PoC, нагрузка MUP мала (05).
- **Требование / риск:** R3 (доступ только друзьям), US-03, US-05, US-06.
- **Варианты:**
  1. Один FastAPI-процесс с модулями: аутентификация, дружба, места и рекомендации, списки, геокодирование.
  2. Отдельные службы: пользователи, лента, места, геокодирование.
  3. Готовый backend как услуга (например, Supabase или Firebase).
- **Решение:** вариант 1. Правило видимости — один подзапрос «я + мои друзья» (`backend/app/api.py`), им пользуются и лента, и сохранение в списки; транзакции в одной БД.
- **Отвергнуто:** вариант 2 — правило доступа пришлось бы дублировать или вызывать по сети, больше точек отказа, не по силам команде за 2 дня. Вариант 3 — противоречит принятому стеку (слайд 8, C4) и переносит данные пользователей на внешнюю площадку.
- **Последствия:** просто развернуть и тестировать (К3 — один автотест); масштабирование только целиком; при росте модули можно выделять по их границам.
- **Условия пересмотра:** нагрузочный тест показал, что один экземпляр не держит целевую нагрузку; или появится независимая по нагрузке часть (уведомления).
- **Затронутые элементы C4:** Backend API, Primary Database.

## ADR-2. Поставщик карт для RAT-PoC: OpenStreetMap + Nominatim за адаптером

- **Статус:** принято для RAT-PoC (решение команды 15.10.2026, правила Nominatim прочитаны и приняты); пересматривается по итогам RAT.
- **Контекст:** поставщик не выбран; в C4 он показан как внешняя система «Картографический провайдер» без названия.
- **Требование / риск:** R1, R2; US-03, US-09; требование 2 с; RAT К1, К2, К4.
- **Варианты:**
  1. Подложка OSM (`tile.openstreetmap.org`) в Leaflet + геокодер Nominatim.
  2. Яндекс Карты (JavaScript API и Геокодер).
  3. 2ГИС (MapGL и Geocoder API).
- **Решение:** вариант 1. Аргументы: без ключа и договора — можно начать сразу; открытая библиотека Leaflet; поставщик задаётся настройками `TILE_URL`, `GEOCODER_URL` (`backend/app/config.py`), так что замена не требует переписывать клиент.
- **Отвергнуто:** варианты 2 и 3 требуют получения ключа и согласия с условиями до начала работы; для Москвы вероятно точнее (не проверено) — поэтому вариант 2 оставлен как **альтернативный путь** при провале К1.
- **Последствия:** обязательная атрибуция OSM; не больше 1 запроса/с к Nominatim, запрет поиска по мере ввода, кэш на своей стороне; публичные серверы OSM без гарантий доступности (R2).
- **Условия пересмотра:** провал К1 или К2; рост до масштаба, где нагрузка на публичный OSM недопустима (05: при 1 000 активных ≈ 210 запр./с подложки); требования к коммерческому использованию.
- **Затронутые элементы C4:** Картографический провайдер, Backend API (адаптер `backend/app/geocoding.py`), Web Client.

## ADR-3. Подложку карты браузер загружает напрямую, геокодирование — через Backend API

- **Статус:** **предложено** — меняет принятую C4 уровня 2; исходная диаграмма не изменена до согласования. В образце реализовано так, как предлагается.
- **Контекст:** по C4 к картографическому провайдеру обращается только Backend API, связи Web Client → провайдер нет. Карта на экране смартфона — 21 фрагмент изображения на одно открытие (05).
- **Требование / риск:** требование 2 с (К2), R2, правила OSM и Nominatim.
- **Варианты:**
  1. Всё через Backend API, как в C4: сервер скачивает фрагменты подложки и отдаёт клиенту.
  2. Всё из браузера: и подложка, и геокодер напрямую из Web Client.
  3. Подложка — из браузера напрямую; геокодирование — через Backend API.
- **Решение:** вариант 3.
  - Подложка напрямую: не добавляет 21 запрос на открытие к нашему серверу и лишний сетевой шаг; браузер сам кэширует фрагменты, как требуют правила OSM; правила разрешают обычный интерактивный просмотр из браузера.
  - Геокодирование через сервер: правила Nominatim рекомендуют прокси и кэш, лимит 1 запрос/с считается на всё приложение — его можно соблюсти только в одной точке; поставщика можно сменить без обновления клиента.
- **Отвергнуто:** вариант 1 — сервер становится прокси для изображений и первым узким местом без пользы для продукта; правила OSM прямо не рекомендуют собственный кэширующий прокси. Вариант 2 — лимит Nominatim нельзя соблюсти на стороне клиентов, кэш у каждого свой.
- **Последствия:** в C4 нужно добавить связь «Web Client → Картографический провайдер: загружает подложку карты [HTTPS]», а у связи Backend API → провайдер оставить «геокодирует адреса и ищет места».
- **Условия пересмотра:** поставщик, который запрещает прямую загрузку из браузера или требует скрывать ключ.
- **Затронутые элементы C4:** Web Client, Backend API, Картографический провайдер (новая связь).

## ADR-4. Геокодер после RAT: адрес — подсказка, точку подтверждает пользователь

- **Статус:** **предложено** (15.10.2026, по результатам RAT); выбор поставщика до MUP — решение команды.
- **Контекст:** К1 не выполнен: Nominatim — 19 из 30, в том числе находит другие объекты (протокол RAT, «Получилось»). Геокодер Яндекса на тех же данных — 25 из 30, тоже ниже порога 27. Условия Яндекса (п. 6.6.1) запрещают показывать результаты бесплатного Геокодера на подложке OSM; п. 5.1.5 ограничивает хранение ответов 30 днями.
- **Требование / риск:** R1, US-09, US-10; RAT К1.
- **Варианты:**
  1. Оставить Nominatim; адрес — подсказка; пользователь видит точку на карте и поправляет её нажатием.
  2. Геокодер Яндекса при подложке OSM.
  3. Полностью перейти на Яндекс Карты (JavaScript API + Геокодер) или на платный геокодер.
- **Решение:** вариант 1 для Прототипа и MVP; вариант 3 оценить до MUP.
- **Аргументы:** вариант 1 не требует ключа и договора, соблюдает правила OSM (К4 выполнен), а ошибку геокодера исправляет человек, который знает место; сценарий 1 от геокодера не зависит. Реализовано в образце (`AddView.vue`).
- **Отвергнуто:** вариант 2 — запрещён условиями Яндекса (п. 6.6.1), несмотря на лучший результат (25 из 30). Вариант 3 сейчас — меняет подложку и C4, требует ключа, а условие хранения ≤ 30 дней противоречит постоянному хранению координат мест; нужна оценка условий и цены, не проводилась.
- **Последствия:** добавление места по адресу требует от пользователя проверки точки — лишний шаг; часть мест может быть сохранена с ошибкой, если пользователь не проверит. Метрика для MVP (С): доля мест, у которых точку поправили после выбора адреса.
- **Условия пересмотра:** на MVP больше 30% мест поправляют вручную (порог — С, согласовать) или жалуются на неверные точки; выбор варианта 3 по условиям и цене; повтор К1 с новым поставщиком.
- **Затронутые элементы C4:** Web Client (форма добавления), Backend API (адаптер геокодера без изменений), Картографический провайдер.
