## 1.2 Состав C4 (строго по Diagrams.pdf)

**Уровень 1 (стр. 1).** Система **Social Map** (Software System, граница Enterprise).

| Элемент | Тип | Описание на диаграмме |
|---|---|---|
| Гость | Person | Просматривает сервис, регистрируется и входит в аккаунт |
| Авторизованный пользователь | Person | Ищет места, публикует рекомендации, сохраняет места в списки, просматривает ленту друзей |
| Модератор / администратор | Person | Просматривает жалобы и управляет проблемным контентом |
| Картографический провайдер | Software System (внешняя) | Карта, геокодирование адресов, поиск мест |
| Сервис уведомлений | Software System | Формирует и распределяет уведомления о событиях |
| Email provider | Software System (внешняя) | Email-уведомления |
| Telegram | Software System (внешняя) | Уведомления через Telegram Bot API |

Связи: все три роли → Social Map [HTTPS]; Social Map → картографический провайдер [HTTPS API]; Social Map → сервис уведомлений [HTTPS API]; сервис уведомлений → Email provider [SMTP / Email API]; сервис уведомлений → Telegram [Telegram Bot API].

**Уровень 2 (стр. 2).**

| Контейнер | Технология | Ответственность |
|---|---|---|
| Web Client | Vue.js | Одностраничное приложение: карта, лента рекомендаций, списки мест, профиль, формы создания публикаций |
| Backend API | Python, FastAPI, SQLAlchemy | REST API, аутентификация, логика рекомендаций, списков, дружеских связей, ленты, локальное хранение медиафайлов |
| Primary Database | PostgreSQL | Пользователи, места, рекомендации, списки, дружеские связи, жалобы, настройки приватности, пути к медиафайлам |

Связи: роли → Web Client [HTTPS]; Web Client → Backend API [REST / JSON / HTTPS]; Backend API → Primary Database [SQLAlchemy / SQL]; Backend API → картографический провайдер [HTTPS API: карты, геокодирование, поиск мест]; Backend API → сервис уведомлений [HTTPS API: новая рекомендация, комментарий, приглашение].

Обе диаграммы читаются полностью.

## 1.3 Противоречия и пробелы

| № | Что | Где | Как решено |
|---|---|---|---|
| 1 | Подписи этапов в исходном промпте сдвинуты относительно слайда 9 | промпт против слайда 9 | используется слайд 9: RAT-PoC → Прототип → MVP → MUP |
| 2 | В C4 есть комментарии, приглашения, жалобы, модерация, приватность, медиа, Email и Telegram — в питче их нет | Diagrams.pdf против питча | в карте историй: модерация — Should, уведомления — Could, комментарии и приглашения — Won't до согласования (С) |
| 3 | К картографическому провайдеру обращается только Backend API, связи Web Client → провайдер нет | Diagrams.pdf, стр. 2 | ADR-3 «предложено»; исходная диаграмма не изменена |
| 4 | Сервис уведомлений нарисован отдельной Software System — неясно, внешний он или собственный | стр. 1–2 | Н; в образце не реализован |
| 5 | Название: «Social Map» на диаграммах, «По Следу» в питче | — | С: использовать «По Следу» |
| 6 | Требование на 1 000 активных пользователей не следует из цифр питча (15 регистраций на MUP, SOM 2–5 тыс.) | — | расчёт на 1 000 показан как оценка, не как требование RAT (05) |
| 7 | В образце статические файлы Web Client отдаёт процесс Backend API | реализация против C4 | это способ развёртывания образца; логически Web Client остаётся отдельным контейнером (С: отдельный веб-сервер на этапе MVP) |

## 1.4 Предлагаемые определения метрик MUP (С)

| Метрика из питча | Предлагаемое определение | Как измерить |
|---|---|---|
| 15 регистраций | число созданных аккаунтов за период MUP, без тестовых | запрос к таблице пользователей |
| 1 рекомендация на пользователя в неделю | (число новых рекомендаций + сохранений в списки за 7 дней) ÷ число зарегистрированных к началу недели | запросы к таблицам рекомендаций и списков; нужна дата сохранения (`added_at` уже есть) |
| Возврат 25% за неделю | доля пользователей, открывших сервис в день 2–7 после регистрации | нужен журнал входов/открытий — в образце отсутствует (Н) |
